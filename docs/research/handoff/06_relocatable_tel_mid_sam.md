> Implementation-research spec for a fresh implementer. Read HANDOFF_README.md first for codebase orientation + non-negotiables.

## Summary
Four interlocking features that close the cluster's strategic loop: shoot-and-scoot makes the existing back-plot (sim/commander.py LaunchCluster) a survivable threat instead of an unused one; a mid-SAM (Buk 9M317 long-reach + 9M338 agile, as two SamDefs) fills the measured Pantsir(20km)<->S-300(150km) gap and shelters the 18km drone; a counter-battery/early-warning (CBR/EW) radar reads inbound StrikeMissile/StealthTargetSam tracks early and back-plots the SHOOTER so the player gets warning + a counter-fire cue; decoy emitters spoof the enemy's ESM fix (sim/enemy_strikes ESM + commander.update_emitter) and corner reflectors seed false back-plot clusters. All four are built against the REAL data models I read: SamDef + SamMissile (per-round loft already supports two rounds, proven by 48N6/40N6), the salvo-tube dict pattern in world/combat.py _oniks_tubes/_s300_tubes, the PantsirDefenseController player-side mirror, the EnemyPicture/back-plot sensor-only brain, the CombatConfig armory + setup screen, the tactical_map RMB/LMB tasking, and the keybinds/controls platform cycle. Every outcome stays physics-not-dice (relocate exposes a real stale-fix; decoys feed a real false fix; CBR reads real tracks), fog-of-war honest (enemy reads only EnemyPicture/RWR-equiv; player CBR reads only its own radar gate), and deterministic (seeded child streams [seed, tag], new tags 8/9/10/11 to avoid collision with the used 3..7). The biggest cross-feature dependency is that ALL of these only pay off once the launch-site back-plot reliably fires — GAME_ANALYSIS.md §5 flags the current back-plot as too timid (mis-projects a sea-skimmer ~12 km), so the relocate + decoy + CBR triad should be specced and balanced AFTER (or alongside) a back-plot reliability pass, else there is nothing to scoot away from.

## Feature: Shoot-and-Scoot Relocatable TEL (RELOCATE order)  _(effort: L)_

**What it is + real-world grounding:**

After firing, a Bastion/S-300/Buk TEL can be ordered to a new map position; while moving it is COMMITTED (cannot launch) and exposed, and on arrival the enemy's back-plotted launch cluster points at the STALE pad. Grounded in real coastal-defence doctrine: the Bastion-P (K-300P) and Iskander/Buk TELs are designed for ~5-min shoot-and-scoot displacement specifically to defeat counter-battery back-azimuth fixes. This is the headline mechanic that turns sim/commander.py's existing LaunchCluster (centroid of ≥3 back-plots within 3 km) from a curiosity into a threat the player actively dodges.

**Platform (launched from / carried by):**

The Oniks Bastion TEL(s) (world/combat.py _oniks_launcher_positions + _oniks_tubes), the S-300 TEL(s) (_s300_launcher_positions + _s300_tubes), and the new Buk mid-SAM TEL. Mechanic is generic over a 'relocatable launcher' so all three reuse it. The radar station and Pantsir are NOT relocatable in v1 (fixed sites — keeps scope to the firing TELs that the back-plot actually targets).

**Sensors (uses / detected by):**

None added on the player side beyond what exists. CRITICAL fog interaction: a MOVING TEL must keep being detectable to the enemy exactly as before — it does not emit, so the enemy can only re-localize it through a FRESH back-plot from a NEW launch (sim/commander.process_missile_track surface intersection at HOME_COAST_Z / time-back-projection). The relocate is effective precisely because the old cluster's fixes are stamped at the old XZ and age out (commander.prune_missile_tracks BACKPLOT_MAX_AGE_S=30s + cluster fixes persist but point at the empty pad).

**AI brain (how the enemy commander uses or counters it):**

No new AI code — the win is emergent. The commander already fires TOMAHAWK_SALVO / JASSM_PACKAGE at LaunchCluster.centre (sim/commander._doctrine_kill). After a relocate, the strike rounds fly to the stale centroid; _refine_strike_aim (world/combat.py) finds NO live structure within SEEKER_BASKET_M=1000m of the empty pad, so the round hits dirt — a clean miss that EMERGES from the player having moved, never a roll. To make the dodge meaningful the enemy must be able to RE-form a cluster from post-move launches: verify the new TEL XZ feeds the next back-plot (it does — back-plot reads the missile's first-seen pos/vel, which now originates at the new pad). Optional Phase-2 brain polish: the commander could mark a cluster 'stale' after a salvo lands with no observed structure-kill (BDA already exists for HARM via mark_emitter_destroyed) — but v1 needs nothing.

**Player UX:**

New 'relocate' interaction on the tactical map (M). While a relocatable platform is the active_platform (TAB) and NO round is selected, RMB on a map point orders a MOVE there (distinct from the launch-waypoint RMB by platform context, exactly like the drone's append_waypoint branch in tactical_map._rmb_waypoint). A dashed move-route line + ghost destination marker draws from the TEL's current pad to the destination. A HUD/map status shows RELOCATING <eta>s and the launcher status flips to MOVING (a third state beside ARMED/RELOADING). X cancels a queued move before it starts. While MOVING, SPACE refuses with a hint 'TEL RELOCATING — CANNOT FIRE'.

**UI needs:**

(1) tactical_map: a move-route polyline (new colour, e.g. amber dashed RELOCATE_COL) + destination ghost-TEL marker; reuse _poly_world + the waypoint-diamond drawing. (2) A MOVING launcher status in _chrome's status strip (new colour beside ARMED_COL/RELOAD_COL) showing 'MOVING <eta>s'. (3) HUD top-left telemetry: a relocate line when the active platform is mid-move. (4) Map hint string addition to MAP_HINT mentioning relocate. (5) The TEL render: game/sandbox._draw_tel must lerp the drawn TEL position along the move (the _tel_positions / _sam_tel_positions lists become time-varying).

**Game-model mapping (reuse vs add):**

REUSE the tube-dict pattern. Add per-launcher state to world/combat.py: each Oniks/S-300/Buk launcher gets a dict {pad_xz, dest_xz|None, move_left_s, committed:bool}. New constants: RELOCATE_SPEED_MPS (TEL road speed ~12 m/s ≈ 43 km/h, open-source K-300P/Buk), RELOCATE_SETUP_S (emplace/displace dwell each end, ~30-45 s, during which it's committed but the move hasn't started/finished). launcher_armed / sam_launcher_armed gain a `and not launcher.committed` clause. The launch tube positions (_oniks_tubes[i]['pos'], _s300_tubes[i]['pos']) must be recomputed from the launcher's LIVE pad when it arrives (today they're baked at build). The destructible Structure wrappers (bastion_tel_NN etc.) must MOVE with the TEL so a strike at the OLD pad misses and a strike at the NEW pad can still hit — Structure.pos + .obb must be updated each step from the launcher pad (this is the load-bearing fog/honesty link). New world API: request_relocate(platform, dest_xz) -> bool; per-step _step_relocations(dt) advancing moves and re-pinning tube + structure positions.

**Implementation sketch + test contracts:**

Files: world/combat.py (state + _step_relocations + request_relocate + arm gates + move the Structure.pos each step), game/sandbox.py (relocate request plumbing + _draw_tel lerp + a 'relocate' branch in request intent), game/tactical_map.py (_rmb_waypoint relocate branch + move-route draw + _chrome MOVING status), game/controls.py/keybinds.py (optional dedicated 'relocate' confirm key, or reuse RMB-on-active-platform). New constants in world/combat.py: RELOCATE_SPEED_MPS=12.0, RELOCATE_SETUP_S=35.0, RELOCATE_COL in tactical_map. TEST CONTRACTS (tests/test_relocate.py, headless against CombatWorld): (a) request_relocate sets committed=True and launcher_armed False immediately; (b) a launch attempt while committed returns None; (c) after move_left_s elapses, the launcher pad, every tube['pos'], and the matching bastion_tel Structure.pos all equal dest within 1 m; (d) DETERMINISM: same seed+same relocate sequence -> identical positions; (e) FOG/HONESTY: simulate a back-plot cluster at the OLD pad, relocate, fire a TOMAHAWK_SALVO via the commander path, assert the strike's _refine_strike_aim finds no structure within SEEKER_BASKET_M of the stale centre (round hits dirt) AND a NEW launch from the new pad seeds a back-plot near the new XZ. Edge: a relocate ordered mid-reload keeps the tube reload timer running (it re-cocks while driving).

**Counters / balance:**

Player counter to the enemy back-plot: scoot after a salvo. Enemy counter to the player scoot: form a fresh cluster from the next launches (built-in). Balance: RELOCATE_SETUP_S + drive time is a real opportunity cost — the TEL is offline and (during the move) its Structure is still killable if the enemy already has rounds inbound to the OLD pad that happen to overfly the route; the physics (round aims at stale centroid) means scooting EARLY beats scooting LATE. Contract that preserves the good loop: a player who never emits/relocates and never gets back-plotted plays exactly as today (the move state defaults to idle; arm gates unchanged when committed=False).

**Risks:**

Moving Structure.pos every step could desync the OBB sweep in sim/bases.apply_missile_hits_structures if pos and obb cache diverge — must recompute obb from pos (verify Structure rebuilds obb from pos each query, not cached at init). The renderer lerp must not break the TEL-erect animation (_tel_frac). Scope creep: keep radar/Pantsir fixed. If the back-plot is still too timid (GAME_ANALYSIS §5) this feature has nothing to dodge — depends on the back-plot pass.

## Feature: Buk-class Mid-Range SAM, two rounds (9M317 long-reach + 9M338 agile)  _(effort: L)_

**What it is + real-world grounding:**

A ~45-70 km medium SAM TEL filling the measured gap between the Pantsir (20 km, GAME_ANALYSIS §4) and the S-300 (48N6 150 km). Two ammunition types as separate SamDefs, exactly the proven 48N6/40N6 pattern: 9M317 'BUK_LONG' — semi-active-ish longer-reach round (~50-70 km, medium loft, 24 g) for reaching out at fighters/AWACS-cued strikers; 9M338 'BUK_AGILE' (Buk-M3 round) — shorter (~35-40 km) but very high-g (~50 g) agile round to swat HARMs, JASSMs and maneuvering fighters close in and to shelter the loitering drone. Grounded in open-source 9M317/9M317M and 9M338K data (CSIS missilethreat Buk pages).

**Platform (launched from / carried by):**

A new Buk TEL (9A317-class self-propelled TELAR) at the player base cluster, a sibling launcher to the S-300 TEL. Reuses the salvo-tube dict pattern (_buk_tubes) and the relocatable-TEL mechanic (feature 1). Carries its own 9S36-class fire-control radar that JOINS self.radar_net (like the Pantsir radar) — extending the player contact picture at medium altitude/range and sheltering the drone's recon legs.

**Sensors (uses / detected by):**

Uses sim/radar.Radar (its own 9S36 mount, ~70 km fighter/missile, joins radar_net like Pantsir does in sim/pantsir.Pantsir.__init__). The launch reads the gated ContactBoard air tracks (world.contacts.tracks, is_air) exactly as launch_sam does for the S-300 — fog-honest, no truth. The two rounds are SamMissiles guiding on the contact_estimate dead-reckoning closure (_contact_estimate) + truth only at the terminal fuse, identical to S-300/SM-2/Pantsir physics. 9M338 uses its own active seeker (illuminator_pos_fn=None, like the 57E6 and 40N6); 9M317 can also be illuminator_pos_fn=None for v1 simplicity (the SARH illuminator seam is the destroyers' SM-2 detail and not needed to make the round work).

**AI brain (how the enemy commander uses or counters it):**

PRIMARY enemy-AI interaction: the Buk extends the player's no-fly umbrella, so the enemy commander's strike packages (HARM/JASSM at HARM_STANDOFF_M=90km / JASSM_STANDOFF_M=250km, sim/commander.py) now ingress through a medium-SAM threat ring they didn't face before. The 9M338 agile round is the answer to the project's open 'aircraft evasion' gap (enemy_ai_design.md T2) — fighters vectored at the drone (VECTOR_TO_DRONE) or flying SEAD now get shot at inside 40 km and must break (the _assign_air_threats / _evade_threat path already exists and triggers on a player SAM guiding on the fighter — a Buk round guiding on a fighter feeds that same RWR-lock cue with NO new AI code). The HARM threat to the Buk's OWN 9S36 radar is the counter (see counters). No commander code change required for v1; the Buk simply makes the existing strike gauntlet harder, which is the intended skill check.

Recommended: add 'buk' to PLATFORMS_COMBAT (bastion -> s300 -> buk -> drone) and reuse the V round-select key, which now cycles 48N6/40N6 on the s300 platform and 9M317/9M338 on the buk platform. A low-altitude gate hint is NOT needed (both Buk rounds engage low, unlike the 40N6's 4 km floor).

## Feature: Counter-Battery / Early-Warning Radar (CBR/EW)  _(effort: M)_

**What it is + real-world grounding:**

A dedicated player ground radar tuned to catch INBOUND strike/ballistic-class tracks EARLY (longer 'missile'-class range, taller mast for horizon) and to BACK-PLOT the shooter (reverse the symmetric trick the enemy already uses in sim/commander.process_missile_track) so the player gets a timed threat warning AND a counter-fire cue at the launching ship/fighter. Grounded in real counter-battery/EW radars (AN/TPQ-37, 1L13/Casta, Podlet low-altitude EW): the discriminator is early low-altitude detection + trajectory extrapolation to the origin.

**Platform (launched from / carried by):**

A new fixed player ground radar Structure at the base cluster (sibling to the radar_station), built like _spawn_enemy_radars / the radar_station in world/combat.py. Joins self.radar_net like the Pantsir/Buk radars. Destructible (Structure wrapper, on_destroyed clears radar.alive and drops it from the net). Config-gated count (n_cbr).

**Sensors (uses / detected by):**

It IS a sensor. sim/radar.Radar with a TALL antenna (e.g. 30-40 m mast for a better horizon vs 50 m sea-skimmers) and a long 'missile' range (e.g. 180-200 km) but deliberately SHORT 'ship'/'fighter' ranges (it's a missile-warning set, not a surface-search set) so it complements rather than replaces the 18 m station. It feeds the gated ContactBoard (world._player_visible already ORs the radar_net) so inbound Tomahawk/JASSM/HARM/SM-class tracks appear EARLIER on the map. The new piece is a back-plot pipeline that mirrors the enemy's: when this radar holds a young, low, inbound HOSTILE strike track, extrapolate its velocity back to the surface/coast to estimate the SHOOTER position (re-uses the exact math in commander.process_missile_track — BACKPLOT_CLIMB_VY vs level-cruise coast-intersection).

**AI brain (how the enemy commander uses or counters it):**

This is the PLAYER's brain, but it must stay symmetric/honest: the CBR reads ONLY tracks its own Radar.detects() passes (range class + horizon + terrain LOS) — never truth. It produces (a) a THREAT WARNING (count + time-to-impact on the nearest protected structure, computed like PantsirDefenseController._time_to_impact) and (b) a COUNTER-FIRE CUE: a back-plotted shooter estimate that, when it lands on or near a known enemy contact (a destroyer/fighter the player already has a track on), surfaces as a recommended Oniks/Buk target. It does NOT auto-fire (player agency). It interacts with the ENEMY brain indirectly: it rewards the player for letting the enemy shoot first (counter-battery), creating a real tension with radar-silence (a CBR that emits can itself be ESM-localized and HARMed — same EmitterIntel/back-plot the station feeds in _feed_enemy_picture, so the CBR must be added to that emitter feed for honesty).

**Player UX:**

(1) A THREAT STRIP on the HUD/map: 'INBOUND x3 — TTI 47s' driven off the CBR's early tracks (this is GAME_ANALYSIS §7 QOL 'threat-warning HUD strip'). (2) On the tactical map, back-plotted shooter estimates draw as amber 'CB' caret markers with an uncertainty circle (error ~ detection-range fraction, like the ELINT circle). (3) When the player selects the Bastion/Buk and a CB cue exists, a 'COUNTER-FIRE: BRG/RNG' hint or a one-key 'snap target to nearest CB cue'. (4) An R-style silence toggle for the CBR (it emits, so it's locatable) — or it shares the radar_toggle. The CBR marker on the platform-stars overlay shows alive/dead.

**UI needs:**

(1) HUD threat strip widget (new, top-center or under telemetry): inbound count + min TTI, WARN/DANGER colour by TTI. (2) tactical_map: CB-cue markers + uncertainty circles (reuse _elint_overlay circle drawing) and a back-plot ray. (3) A CBR platform star/marker on the map (reuse _platform_stars / _pantsir_markers). (4) Setup Armory/World row for n_cbr. (5) Optional HUD line showing the CBR emitting/silent state.

**Game-model mapping (reuse vs add):**

REUSE three existing pieces: sim/radar.Radar (the set itself), the back-plot math from sim/commander.py (extract the surface/coast back-projection into a shared helper so BOTH sides call it — DRY and guarantees symmetry), and PantsirDefenseController._time_to_impact (for TTI). New: a small sim module sim/counter_battery.py (or a method block in world/combat.py) holding a CbrTracker that each step consumes inbound hostile StrikeMissile/SamMissile(is_hostile) tracks the CBR's Radar.detects() passes, maintains first-seen metadata (mirror world/combat _cmd_missile_intel), and emits {threats:[{tti, pos}], cues:[{shooter_xz, error_m}]}. The CBR radar is added to the enemy ESM emitter feed (_feed_enemy_picture pic.update_emitter) and to _emitters() so it is honestly locatable. CombatConfig gains n_cbr (+ CLAMP_CBR); world builds it in __init__ + a destructible Structure + on_destroyed.

**Implementation sketch + test contracts:**

## Feature: ESM Decoy Emitters + Corner-Reflector Back-plot Decoys  _(effort: M)_

**What it is + real-world grounding:**

Two cheap, deployable spoofers: (1) a DECOY EMITTER — a radiating set that mimics the player radar/CBR signature, drawing the enemy's ESM fix (sim/enemy_strikes ESM + commander.EmitterIntel) and HARM packages onto a worthless decoy instead of the real radar; (2) a CORNER-REFLECTOR / repeater field — a strong false RF return near a fake coastal point that seeds bogus launch back-plots, polluting the enemy's LaunchCluster so its TOMAHAWK/JASSM salvos scatter onto empty ground. Grounded in real EW: inflatable corner reflectors, gap-filler decoy emitters, and towed/expendable repeaters used to fox ARM seekers and ESM back-azimuth (open-source Russian/NATO EW decoy practice).

**Platform (launched from / carried by):**

Static, player-placed ground props at the base cluster, config-gated (n_decoys). The decoy EMITTER is a Radar-like emitter object (only needs .alive/.emitting/.pos/.antenna_alt to be heard by ElintReceiver and the enemy ESM/commander emitter feed) — it does NOT detect anything (it's bait). The corner-reflector is a passive marker that injects false back-plot fixes into the enemy picture when an enemy radar 'sees' a player launch crossing its location. Both are destructible Structures (cheap HP) — the enemy wasting a HARM/TLAM on a decoy is the win.

**Sensors (uses / detected by):**

The decoy emitter is SEEN BY the enemy's sensors: it must appear in world/combat.py _emitters() (the ELINT list) and in _feed_enemy_picture's emitter-accrual loop so commander.update_emitter builds an EmitterIntel/located fix on it — i.e. it rides the SAME passive-ESM pipeline the real radar does. The corner-reflector interacts with the back-plot pipeline: it does not emit, but it biases the shooter back-projection (a strong false return near the reflector pulls the enemy's add_back_plot estimate toward the decoy coast point).

**AI brain (how the enemy commander uses or counters it):**

This is the most direct enemy-AI manipulation in the cluster — and it must stay HONEST (the AI is fooled because its SENSORS are fooled, never because we lie to it). Decoy emitter: the commander's _doctrine_blind schedules HARM packages at ANY located+alive radar EmitterIntel (it iterates picture.emitters). If a decoy emitter is located, the commander may target IT — wasting HARMs (the BLIND-before-KILL gate even stalls the KILL phase while it chases the decoy). To make the decoy attractive but not omniscient-proof, the enemy could (Phase-2 brain) weight emitters by fix quality/persistence — but v1's existing 'first located alive emitter' selection (commander._believed_radar_station returns the first located+alive) means a decoy that lights up and holds a fix genuinely diverts the HARM. Corner-reflector: it adds false BackPlotEntry fixes (via the existing add_back_plot path with a decoy-biased XZ), so a LaunchCluster can form on empty coast and the commander fires TLAM/JASSM there (_doctrine_kill) — a real, sensor-driven miss. No truth leak: the AI acts on a real (planted) sensor event.
